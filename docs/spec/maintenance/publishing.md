# Publish prototype prereleases

## Workflow

Work on a feature branch and merge through a pull request into `main`.
The `ci.yml` workflow validates branches, pull requests, and manual runs.
A push to `main` in `dziegelbauer/LinqToFile` also publishes after all platform validation jobs succeed.
The push event supports merge, squash, and rebase merges.
Enforce pull requests with a GitHub branch ruleset; a direct push to `main` would also trigger publishing.

The publish job downloads the Linux job's validated package from the same workflow run.
It does not rebuild the package or fetch an artifact from another run.
Windows, Linux, and macOS validation must all succeed before the publish job starts.
Feature branches, pull requests, tags, and manual runs do not publish.

## One-time account setup

1. Create a GitHub environment named `nuget` in this repository.
2. Restrict that environment's deployment branches to `main`.
3. Set its `NUGET_USER` variable to the nuget.org profile name used for login, not an email address.
4. On nuget.org, create a Trusted Publishing policy with these values:

| Field | Value |
|---|---|
| Repository owner | `dziegelbauer` |
| Repository | `LinqToFile` |
| Workflow file | `ci.yml` |
| Environment | `nuget` |
| Package pattern | `LinqToFile` |
| Scopes | Create the package and publish new versions |

Select the NuGet account or organization that will own the package.
The policy must permit the login profile to publish for that owner.
Use the workflow file name only, without `.github/workflows/`.
For fully automatic publication, do not add a required manual reviewer to the environment.
No long-lived NuGet API key is required.
See the [NuGet Trusted Publishing instructions](https://learn.microsoft.com/en-us/nuget/nuget-org/trusted-publishing).

Create a branch ruleset for `main` that requires pull requests and the platform validation checks.
Keep the publishing check out of required pre-merge checks: it runs only after a merge.

## Versions and retries

`Directory.Build.props` contains the local base prerelease version.
CI appends `.ci.<github.run_number>`, for example `0.1.0-alpha.9.ci.123`.
Each new workflow run gets a distinct version.
Rerunning the same workflow run keeps its version.
`--skip-duplicate` permits retrying a publication that already succeeded without replacing the existing package.
No stable release version is generated by this workflow.

The `LinqToFileVersion` environment property supplies the same version to builds, packs, and sample package references.
`eng/Verify-Package.ps1` also uses it, or accepts `-PackageVersion` explicitly.
Local builds without this override retain the base version.
Increase the base prerelease version when changing release series.
If the workflow is replaced and its run counter resets, increase the base version before publishing again.

NuGet versions cannot be overwritten.
Corrections require a new version from another successful main run.
The workflow summary identifies the package version. Packages can take time to appear in NuGet search.

## Local verification

Use PowerShell 7 from the repository root:

```powershell
$env:LinqToFileVersion = ./eng/Get-CiVersion.ps1 -RunNumber 123
dotnet build LinqToFile.sln -c Release -warnaserror
dotnet test tests/LinqToFile.Tests -c Release --no-build --no-restore
dotnet pack LinqToFile -c Release --no-build --no-restore -o artifacts/publishing-feed
./eng/Verify-Package.ps1 -RuntimeIdentifier osx-arm64 -PackageDirectory artifacts/publishing-feed
Remove-Item Env:LinqToFileVersion
```

Use the runtime identifier for the local machine.
These commands validate a local artifact. They do not authenticate with NuGet or publish it.
