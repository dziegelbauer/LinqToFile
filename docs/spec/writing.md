# Writing and row insertion planning

## Confirmed objective
- Add write capability with an API intuitive to LINQ/EF Core users.
- Begin with inserting or appending one or more rows to a file.
- Implement CSV writing first. XLSX writing is future work.
- Support both appending records and inserting records at a specified row position.
- Use direct write operations that execute when called, rather than staging Add/AddRange calls for SaveChanges.
- Async operations are AppendAsync(record), AppendRangeAsync(records), InsertAsync(long position, record), and InsertRangeAsync(long position, records). Range inputs support IEnumerable<T> and IAsyncEnumerable<T>; all async operations accept an optional CancellationToken.
- Include synchronous Create, Append, AppendRange, Insert, and InsertRange methods in the first implementation. They return long and accept ordinary records or IEnumerable<T> as applicable. IAsyncEnumerable<T> inputs are supported only by async methods; do not block on async enumeration to implement sync writes.
- TabularFile.Csv<T>(path) returns CsvFile<T>, exposing both read and write operations with shared fluent reading/writing options. Supplied-stream and factory overloads remain read-only CsvSource<T> sources. Fluent options preserve the distinction and return the corresponding source type, so unsupported writes fail at compile time. Preserve compatible existing read usage where possible; validate public API changes against the prototype package.
- Creation uses file.CreateAsync() for headers only and file.CreateAsync(initialRecords) for headers plus initial rows.
- Creation with initial data and both range operations accept IEnumerable<T> and IAsyncEnumerable<T>. Process records incrementally without materializing the complete input sequence.
- An empty append/insert range leaves the destination unchanged but still validates file existence, headers/schema, insertion index when applicable, and existing-data validation under the selected mode. Do not replace the file or add separators for an empty range. Creation with an empty initial sequence writes headers only.
- Successful write operations return the number of data rows written as long; async methods return ValueTask<long>. Headers do not count. Headers-only creation and empty append/insert ranges return 0. Single-record append/insert returns 1 on success.
- Default append/insert behavior prepares the complete result in a temporary file beside the destination, then replaces the original only after preparation succeeds. Errors or cancellation before replacement leave the original unchanged; append also pays the cost of copying the existing file.
- In the default temporary-file mode, honor cancellation until immediately before replacement begins. Once replacement starts, stop observing the operation token; successful replacement reports success even if cancellation is requested during or after that step. Replacement failures still throw; the filesystem and durability policy is specified below.
- WithMaxFieldLength(...) and WithMaxRecordLength(...) apply to newly serialized rows and generated headers using the existing reader's counting rules: unescaped UTF-16 field units before trimming, and source UTF-16 record units including delimiters/quotes/embedded newlines but excluding the record terminator. These output checks remain enabled during quick append.
- The default mode requires the filesystem's same-directory replacement operation for an existing destination. Unsupported or failed replacement throws; never automatically fall back to in-place writing or a destructive delete/copy sequence. Do not promise durability through crashes or power loss. Verify platform/filesystem behavior with narrow probes before choosing the BCL replacement primitive; creation still requires non-overwriting publication.
- WithInPlaceWrites(bool enabled = true) opts into direct writes without temporary files. Its default configuration is disabled, so writes use temporary-file replacement unless opted in. Both append and positional insertion support in-place mode. Insertion appends the new block and rotates it before the suffix using fixed-size buffers; it does not use temporary storage or whole-input materialization.
- Permit only one active library write per normalized file path within a process. Overlapping write attempts fail immediately rather than queue. Coordination between writers in separate processes is the caller's responsibility. Path normalization, alias handling, and read/write sharing details remain engineering/design questions; do not claim a cross-process lock or filesystem-identity guarantee.
- In the opt-in in-place mode, disk failures and input-sequence errors may leave partial changes. This risk is accepted; no rollback guarantee is provided.
- For in-place writes, honor cancellation during preparation but stop observing the operation's cancellation token immediately before the first operation that modifies the destination, including a write or length change. Once mutation starts, do not pass that token to subsequent I/O or input enumeration, or report cancellation merely because that token becomes cancelled. This prevents operation-token cancellation from interrupting an in-place modification; it does not establish rollback or validity guarantees for I/O failures, input-sequence failures, independent cancellation, or process termination.
- Insertion uses a zero-based data-row index, excluding the header: 0 inserts before the first data row; an index equal to the existing data-row count appends. Negative indexes and indexes greater than that count throw.
- Insertion indexes use long, matching the data-row count type and supporting files with more than int.MaxValue records.
- Insertion indexes count logical CSV data records, not physical lines. Quoted multiline fields remain part of one record. Blank physical lines skipped under the configured reader options do not count toward the index.
- When inserting before an existing data record, place new records immediately before that record, after any skipped blank lines preceding it. Insertion at the data-row count appends at physical EOF, after any trailing blank lines. Preserve those existing blank-line bytes.
- By default, append and insert validate the entire existing CSV's syntax and row widths before modifying the destination. Malformed quoting or inconsistent row widths throw and leave the original unchanged, including in in-place mode. Do not convert existing field values to model types during this validation. This requires a full scan even for append; temporary-file preparation may combine validation with copying as long as the destination remains unchanged until validation succeeds.
- WithAppendValidation(bool enabled = true) controls full validation of existing data for append operations; it is enabled by default. WithAppendValidation(false) selects quick append. Positional insertion always retains full existing-file validation. Quick append retains file-existence checks, valid headers with exact model/schema matching, and validation of newly written rows. This option is independent of WithInPlaceWrites: skipping validation does not itself disable temporary-file replacement or its full-file copy; combining both options avoids the full-file scan and copy.
- Initial write destinations are file paths only. Writable supplied streams and stream factories are deferred to the roadmap; their seeking, ownership, and partial-write contracts remain future decisions.
- Insert and append require an existing file to confirm developer intent; they must not implicitly create a missing destination.
- Provide an explicit file-creation operation accepting an optional initial data set. Creation is part of the write scope.
- Creation throws if the destination already exists; it must not overwrite an existing file.
- Creation uses the same two write modes: by default, prepare headers and initial rows in a temporary file beside the destination, then publish without overwriting any existing destination. WithInPlaceWrites() creates the destination directly, and failures may leave a partial file. Neither mode permits overwriting an existing file. Default creation honors cancellation until immediately before non-overwriting publication; direct creation honors it until immediately before FileMode.CreateNew opens the destination. No operation-token cancellation is observed after the respective boundary.
- Insert and append reject an existing zero-byte file because it has no valid header. A valid header-only CSV accepts records; its data-row count is zero, so insertion index 0 is valid.
- Reuse TabularRecord, Column, and Ignore annotations for writing. Generate direct property access at compile time; do not use runtime reflection.
- Writing requires a getter accessible to the generated mapper for every mapped property. The user approved retaining reads for setter-only models and rejecting their writes before any file creation, including headers-only creation.
- For existing files, serialize values in the existing file's header order, even if it differs from model property order.
- Newly created files order headers alphabetically by mapped column name using ordinal comparison. Use Column annotation names when present and property names otherwise; exclude Ignore members. This order is deterministic across partial classes and inheritance and does not alter existing-file header order.
- Preserve existing content byte for byte, including quoting, whitespace, and record endings. Serialize only new rows and add separators where necessary; appending after a final record without an ending adds a separator before the new rows.
- For new rows in an existing file, use the header record's line ending by default. New files default to Unix-style LF, independent of platform. If the header has no terminator, fall back to LF. WithNewLine(LineEnding value) explicitly overrides the line ending used for newly serialized content in either case; existing bytes remain unchanged. The enum members are LineEnding.CrLf, LineEnding.Lf, and LineEnding.Cr.
- Configuration choices must use enums or other typed options rather than magic strings. This does not prohibit strings for user-provided paths, names, or other free-form values.
- Newly created CSV files default to UTF-8 without a BOM. WithEncoding(...) can configure another encoding.
- For existing files, encode new rows with the encoding selected by the existing BOM-detection and WithEncoding(...) rules. Preserve the existing BOM bytes unchanged; append and insert never emit another BOM. Existing content remains byte-preserved.
- Serialize new fields with minimal quoting: quote a field when it contains the configured delimiter, configured quote character, CR, or LF; double embedded quote characters inside quoted fields. Preserve field whitespace rather than trimming it during writing.
- Exception to minimal quoting: a single-column row with an empty value writes an explicitly quoted empty field using the configured quote character, rather than a blank line, so default blank-line skipping does not discard the record.
- Null values serialize as empty CSV fields. Empty strings also serialize as empty fields; null strings therefore read back as empty strings under the existing reader rules. Preserve the single-column quoted-empty exception for either case.
- Reject a null record argument or a null record within an input range by throwing. This is distinct from null property values, which remain valid empty fields. A null item discovered during input enumeration follows the selected write mode's existing failure guarantees.
- Honor the same WithDelimiter(...) and WithQuote(...) settings used for reading, including non-default characters, throughout creation, existing-file validation, header serialization, field separation, quoting/escaping, and empty-field quoting. Do not hard-code commas or double quotes. Include non-default delimiter/quote combinations in write and read-back validation.
- Format numeric values with the configured WithCulture(...) snapshot, defaulting to InvariantCulture. Preserve round-trip precision for floating-point values and reject NaN and positive/negative infinity. Exact per-type format choices must remain compatible with the existing readers; do not introduce grouping or currency syntax that they reject.
- Serialize booleans as lowercase true/false and GUIDs in the standard hyphenated form. Serialize enums using declared names, including comma-separated names for flags; reject values that cannot be represented by the reader's supported named-value rules. Generate enum serialization without runtime reflection. Deterministic alias selection and flags decomposition remain engineering details to specify and test.
- For DateTime values, accept only DateTimeKind.Unspecified and write without an offset. Reject Local and Utc values rather than discarding kind/offset information or performing implicit timezone conversion. DateTimeOffset serialization preserves the explicit offset.
- Serialize temporal values using invariant round-trip text: ISO dates/times with full tick precision and preserved explicit offsets, plus a fixed culture-independent TimeSpan duration format. The reader must recognize these writer formats independently of WithCulture(...), while retaining the established DateTime kind/offset rules. Verify and adjust reader compatibility as needed, with tests for non-Gregorian cultures, precision, boundaries, and any parsing-precedence changes. Exact lexical forms remain to be specified.
- Writing requires an exact match between mapped model columns and file headers under the configured header comparer. Missing or extra columns throw; different column order is valid. This write-specific rule does not change reading's policy of ignoring unmapped extra columns.
- Append supports UTF-8/16/32 and stateless single-byte encodings. Other encodings throw before mutation. The user approved this restriction after the stateful-encoding probe; reading and creation retain their current encoding support.
- Serialization failures use TabularWriteException, identifying the input record and mapped column/member when available, without raw values. Header/schema failures reuse TabularSchemaException. I/O and cancellation retain their standard .NET exception types. Exact diagnostic properties and input-record numbering remain to be specified consistently with existing diagnostics.
- Preserve .NET 10+, cross-platform, Native AOT, BCL-only runtime, no runtime reflection, and minimized allocations.
- Plan with the user before implementation. Current branch: feature/row-writing-plan.

## Stage 1 implementation choices
- Keep generated scalar formatting separate from CSV escaping and file mutation for later formats.
- Reject undefined LineEnding values immediately, consistent with existing option validation.
- Exact scalar formats, enum alias/flags rules, diagnostic numbering, and probe results are recorded in [stage 1 validation](history/validation-writing-stage1.md).

## Stage 2 implementation choices
- Append and range append are implemented for synchronous/asynchronous inputs and both mutation modes, with exact file-order binding and default syntax/width validation. Quick append keeps header/schema/encoding/new-row checks without body parsing.
- Default replacement uses File.Replace with no fallback. In-place async enumeration uses a cancellation-forwarding gate until the first destination write, then stops forwarding the operation token.
- NewLine is nullable internally to distinguish an explicit LF override from header inference. BOM-selected encodings retain configured encoder and decoder fallback policies.
- Unix temporary copy permissions are restricted to the original rwx bits and process umask; ownership/ACLs and other metadata are not generally preserved. Sharing and replacement behavior follows the filesystem.
- Tests, narrow probes, allocation checks, and package/AOT results are recorded in [stage 2 validation](history/validation-writing-stage2.md).

## Stage 3 implementation choices
- Insertion shares the existing-file encoding boundary used by append, full schema/parser validation, generated formatting, guards, cancellation gates, and staged permission rules. Long logical indexes preserve skipped blank-line placement and multiline records.
- PositionedTextReader records original byte offsets while decoding stateless units; it does not infer offsets by re-encoding old fields. Nonempty insertion at a boundary inside a multi-record decoder replacement throws NotSupportedException before mutation; an empty valid range remains a no-op.
- Default insertion stages prefix/new rows/suffix. In-place insertion writes the unknown-length new block at EOF and rotates it before the suffix with two 64 KiB buffers and three reversals. No input replay, hidden spill, or whole-input collection is used.
- Async movement flushes asynchronously before seeks to avoid hidden synchronous buffered data writes. Operation cancellation is ignored after the first in-place write, including through suffix movement.
- Full scans track the decoded EOF terminator, so ignored trailing bytes do not create spurious blank records. The shared preparation class is now CsvWritePreparation. IWriteFileSystem is an internal deterministic fault-test seam, not a public provider API.
- Package/AOT results, allocation bounds, disk probes, and fault/cancellation evidence are in [stage 3 validation](history/validation-writing-stage3.md).

## Engineering checks and remaining work
- Stage 2 probe found an encoding contract question. A valid ISO-2022-JP CSV ending in Japanese shift state reads correctly, but appending a fresh encoder's newline/row causes strict decoding failure. A final ASCII-reset sequence is optional in existing input. The ignored BCL probe lives in artifacts/append-probes; it uses CodePagesEncodingProvider explicitly in the probe only. The runtime library has not registered a provider or changed encoding support.
- Confirmed by the user: initially permit append for UTF-8/16/32 and stateless single-byte encodings; reject stateful/unsupported encodings before mutation while preserving their existing reading/creation support. Do not scan the whole file in quick mode or claim generic encoder continuation is safe.
- See [implementation plan](writing-plan.md) for sequencing and acceptance checks. Stages 1–3 are implemented; performance/release validation remains stage 4.
- Verify byte-preserving record boundaries for supported encodings, including BOMs, multibyte sequences, CRLF, and EOF. Investigate stateful/custom encoding constraints before promising support or narrowing the agreed WithEncoding behavior.
- Verify the bounded-memory, single-enumeration in-place insertion algorithm and cancellation cutoff. Do not solve unknown input size with whole-input buffering or a hidden temporary file.
- Probe same-directory replacement/non-overwriting publication across the platform matrix; document permissions, metadata, links/aliases, open readers, and unsupported filesystem behavior accurately.
- Specify exact scalar lexical forms, deterministic enum aliases/flags, and culture-independent temporal recognition without silently changing existing reader semantics. Probe non-Gregorian cultures and ambiguous parsing precedence.
- Complete method signatures and diagnostic numbering consistently with approved long indexes/counts and existing errors. Creation cancellation follows the approved first destination mutation/publication boundary.
- Quick append intentionally omits existing-data validation; it cannot guarantee that an already malformed file will become valid. Preserve the agreed header/new-row checks and do not silently repair old content.
- Buffer sizes, pooling, path-registry lifetime, and cleanup mechanics are engineering choices guided by measurements. Stop and ask if a probe exposes a required public behavior change.

## Scope boundaries
- Stages 1–3 implement CSV path creation, append, and insertion. Stage 4 remains.
- Updates, deletes, general entity tracking, and transactional behavior require separate decisions.
- Keep unimplemented work on the public roadmap; publish usage documentation only when behavior exists.
